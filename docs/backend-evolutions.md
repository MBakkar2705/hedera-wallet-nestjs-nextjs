# Backend evolutions to consider

Changes in `backend/` (mostly `backend/src/`) and two in `frontend/` (items 19 and 29) that would help the frontend or the project. Items marked **Done** were made in a merged lot (see "Backend evolutions" in the README); the others are not done. Each item says how it is known: **Observed** (seen when running the application) or **From the code** (read in the source, not tested).

1. **Done (lot Error handling, ADR 0014). An unknown account returned 500, not 404.** Observed: a lookup of an unknown account ID returned HTTP 500 "Internal server error", and the backend log showed the Hedera status `INVALID_ACCOUNT_ID`, wrapped by `getAccountInfo` in a plain `Error`. Result: a global filter turns it into HTTP 404 (observed with curl: `Hedera does not know this account (INVALID_ACCOUNT_ID)`), and a malformed ID such as `abc` into HTTP 400.
2. **Done (lot Error handling, ADR 0014). Other Hedera errors returned 500 too.** Observed: a transfer from an account whose balance was lower than the amount returned HTTP 500 (log: `INSUFFICIENT_PAYER_BALANCE`). Result: the same filter turns it into HTTP 400 with `Hedera rejected the request: INSUFFICIENT_PAYER_BALANCE`. Also observed after the change: an unknown recipient of a transfer gives 404, an unknown topic gives 400 (`INVALID_TOPIC_ID`), and a key that did not match the account showed `INVALID_SIGNATURE` on the transfer page. The routes of the tokens go through the same filter but were not tested.
3. **Done (lot Token responses, ADR 0015). The account lookup returned token IDs only.** Observed: an account that received 10 tokens showed `Token associations: 1` and nothing else. From the code: `tokenAssociations` was built from `rel.tokenId.toString()`. Result: the response also has `tokens`, a list of `{ tokenId, symbol, balance }`, next to `tokenAssociations`, which is kept. Observed: for the account `0.0.6106565`, `tokens` holds 285 entries, the same number as the public mirror node, and the frontend lists them with symbol, ID and balance. The `balance` of a token is in its smallest unit: the decimals of a token are not returned, and a token with decimals other than 0 was not tested.
4. **Done (lot Token responses, ADR 0015). Amounts were formatted strings.** Observed: `hbarBalance` was `"3.99888384 ℏ"` and the `amount` of a transfer `"1 ℏ"`. Result: the account response also has `balance` (`hbar` and `tinybars`, two strings), and the transfer response has `value` (a number) and `unit` (`"HBAR"`), next to the old fields, which are kept. Observed with Swagger: a transfer of 1 HBAR answers HTTP 201 with `"amount": "1 ℏ"`, `"value": 1` and `"unit": "HBAR"`. The old fields can be removed only by a later decision. From the source of the SDK (read, not run): `hbarBalance` still changes its unit with the amount.
5. **Done (lot Token responses, ADR 0016). There was no endpoint to list the tokens.** From the code: created tokens are saved in SQLite (`TokenEntity`), but nothing read them back. Result: `GET /tokens?page=&limit=` answers `{ items, page, limit, total }`, newest first, from the local table only, so only the tokens created through this backend are listed. Observed with curl and in the frontend: 2 then 3 tokens listed, pages of 1 token, a page after the last one gives an empty list, and `limit=500` gives HTTP 400. The buttons Previous and Next with more than one page were not tested.
6. **The treasury of a new token is always the operator account.** From the code: `createToken` uses the operator account as treasury and admin key. To send the new tokens, the operator key must be typed in the frontend (see ADR 0009).
7. **No authentication, and keys in request bodies.** ADR 0009 states that the backend has no authentication. The tokens controller has no guard, so anyone who reaches the API can create tokens paid by the operator account. Signing with a wallet is the evolution named in ADR 0009.
8. **Minimum amounts.** From the DTOs: a HBAR transfer needs `amount >= 1`, so less than 1 HBAR cannot be sent. Token amounts are integers, and tokens are created with 0 decimals.
9. **Done (lot Configuration, ADR 0017). The CORS origin is written in the code.** `backend/src/main.ts` allowed `http://localhost:3001` only. A deployment would need it to come from a variable. Result: the origin is read from `CORS_ORIGIN` (one origin, default `http://localhost:3001`), the port from `PORT` (default 3000) and the path of the SQLite file from `DATABASE_PATH` (default `hedera-wallet.db`), which lets the end-to-end test use a throwaway file. Observed: with `CORS_ORIGIN=http://localhost:3002`, curl got `Access-Control-Allow-Origin: http://localhost:3002`, and the page `/accounts` on port 3001 then showed "Cannot reach the API" with a CORS error in the console of the browser; `PORT=3005` moved Swagger to that port, and `PORT=abc` stopped the backend with `Invalid PORT "abc"`; with the default path, the page `/tokens` still listed the 3 tokens, and the modification time of `backend/hedera-wallet.db` did not change after `pnpm test` and `test:e2e`. Not tested: the frontend with a changed `PORT` (it needs `NEXT_PUBLIC_API_URL`), and a `DATABASE_PATH` other than the default on the running backend.
10. **Done (lot Configuration, ADR 0017). Two pairs of environment variables** (`OPERATOR_*` and `HEDERA_*`) for what can be one account (ADR 0007). Result: the backend reads only `HEDERA_ACCOUNT_ID` and `HEDERA_PRIVATE_KEY`, in `createHederaClient()`, and one Hedera client is shared by the Hedera, accounts and tokens modules (three clients before). Observed: the backend started with the usual `.env` and with `OPERATOR_ID` and `OPERATOR_KEY` commented out; the account lookup, the creation of a token (`TST4`) and a transfer of HBAR worked; with both variables absent, the backend stopped with `Missing environment variable(s): HEDERA_ACCOUNT_ID, HEDERA_PRIVATE_KEY`. Not tested: the creation of an account, the association and the transfer of a token with the shared client, one variable absent, and the container. Observed later (lot Hygiene and security, note of 2026-10-15 in ADR 0017): the creation of an account, the association of a token and two transfers of tokens with the shared client all worked (`SUCCESS`); still not tested: one variable absent, and the container.
11. **Done (lot Rules and tooling, ADR 0013). The backend lint and the e2e test cannot run.** From the code: `backend/eslint.config.mjs` imports `@eslint/js`, `typescript-eslint`, `eslint-plugin-prettier` and `globals`, none of which is declared in `backend/package.json`, and there is no lint script. `backend/test/app.e2e-spec.ts` imports `supertest`, which is not declared either. Observed: `pnpm test` runs 4 suites and the e2e file is not among them. Neither was run.
12. **A Jest warning** ("worker process has failed to exit gracefully") appeared once, with an unknown cause (ADR 0008). Closed without code: not seen again in at least five runs (reported by the author). To reopen if it comes back.
13. **Done (lot Error handling). Reading the messages of a topic without any message returned 500.** Observed: the /topics page showed its message for an HTTP 500 (the page adds it only when the status is 500). Result: `getMessages` returns an empty list, `GET /topics/0.0.9999999/messages` answers HTTP 200 with `[]` (observed with curl) and the page shows "0 messages". A topic ID that is unknown or malformed also gives an empty list, because the messages are read from the local database only.
14. **The messages of a topic come from the local database only.** From the code: `sendMessage` saves each message in SQLite and `getMessages` reads them back from there, so a message published by any other means does not appear. Observed: the two messages published from the application were listed in order.
15. **Done (lot Rules and tooling, ADR 0005). Ctrl+C does not stop the Docker container.** Observed: after the documented `docker run` command, Ctrl+C in the terminal left the container running and `docker stop` was needed. The cause was not investigated. The `--init` option of `docker run` is a possibility to test. Result: with `--init`, Ctrl+C stops the container in about 2 seconds; without it, Ctrl+C has no effect after about 30 seconds and `docker stop` takes about 10 seconds (observed).
16. **Done (lot Strict TypeScript, ADR 0018). The backend did not use TypeScript strict mode.** Observed: `backend/tsconfig.json` had `strictNullChecks: true`, `noImplicitAny: false` and `strictBindCallApply: false`, without `strict`; the frontend uses `strict: true`. Measured by the author on 2026-10-14 (nothing modified, `tsc --noEmit` with `--strict --noImplicitAny --strictBindCallApply`): 75 errors, all `TS2564`, in 15 files (6 entities and 9 DTO), with `tsconfig.build.json` and with `tsconfig.json` alike; the earlier measure, made when this item was written, was 49 errors in 12 files. Result: `backend/tsconfig.json` has `"strict": true` (the three explicit lines are removed) and each of the 75 properties is declared with `!` (the first option of ADR 0018, chosen against initial values and `strictPropertyInitialization: false`). Observed by the author: `tsc` prints nothing, `pnpm test` runs 7 suites and 46 tests, and the lint, the format check, `test:e2e` (7 tests) and `pnpm --filter backend build` pass; the compiled JavaScript (70 `.js` and `.d.ts` files) is identical before and after; the backend starts, `GET /tokens` answers the 4 tokens saved, the pages `/tokens` and `/accounts` behave as before and Swagger lists the schemas of the responses; the CI is green. Not tested: any write to the database after the change, and the Docker build. Observed later (lot Hygiene and security): after the change, the backend wrote rows in the six tables (read in read-only mode on 2026-10-15, see ADR 0021); the Docker build is still not tested.
17. **Done (lot Hygiene and security, ADR 0021). Table names are not consistent.** From the code: `accounts`, `associations`, `tokens`, `token_transfer_entity`, `message_entity`, and `@Entity()` without a name for the topics. With `synchronize: true`, TypeORM does not rename a table: it creates a new one. A renaming therefore needs a choice between an empty database and a migration. Result: the tables are `topics`, `messages` and `token_transfers`, with explicit names, like `accounts`, `associations` and `tokens`; no migration, the author started from a new database file and kept the old one as `backend/hedera-wallet.old.db` (29 rows, not carried over). Observed: the old file (read-only, by the assistant) had `topic_entity` (6 rows), `message_entity` (8) and `token_transfer_entity` (1); the new file has the six tables with the columns of the entities, an end-to-end test requires exactly these names, and after the change the application wrote rows in each table and the pages `/tokens` and `/topics` listed them. Not tested: what `synchronize` does with an old file, and the container. The README named a table `transfer_entity` that does not exist (HBAR transfers are not stored); it is corrected.
18. **Done (lot Hygiene and security, ADR 0022). Private keys are stored in clear in the database.** Observed (SQLite viewer): the table `accounts` has a `privateKey` column in clear. From the code: the transfers take the keys from the request body, so the stored key is never read back (`git grep accountRepo` on the main branch finds only the creation and the save of the row). Result: the column is removed, `createAccount` saves the account ID, the public key and the initial balance, and `POST /accounts` still returns the key once, so the caller must keep it. The ADR compares encrypting, hashing, keeping in clear and not storing. Observed: the new file has no `privateKey` column; the account `0.0.11035637`, created from the page, has one row without key while the page showed the key, and signed two transfers with it afterwards; an end-to-end test requires the absence of the column. Not tested: that no log prints the key (no log was read), and the old copy `hedera-wallet.old.db` still holds the 8 old keys on the disk of the author.
19. **Done (lot Frontend CSP, ADR 0019). Activating an existing account checked only the format of the ID.** Observed: an account ID typed with one digit missing (`0.0.1100279` instead of `0.0.11002792`) was accepted as the active account, and the error appeared only at the first transfer (`Hedera rejected the request: INVALID_SIGNATURE`). From the code (`handleActivate` in `frontend/app/accounts/page.tsx`): only the pattern `^\d+\.\d+\.\d+$` and a non-empty key were checked, and `activate` kept the account in the state of the page without any call to the backend. Result: `GET /accounts/:accountId` also returns `key` (`{ type, publicKey }` for a single key, `null` otherwise), and the frontend compares, in the browser, the public key of the typed private key with it; the private key is not sent, so ADR 0009 is not affected. Observed by the author: the activation succeeded for an Ed25519 account and for an ECDSA account, with the key in DER form and as 64 hexadecimal characters (with or without `0x`); it is refused for an unknown account, for the key of another account (the example of this item), for a key that cannot be read (a text of 63 characters or with a character that is not hexadecimal included, which the browser build of the SDK would read as another key), for an account whose key is not a single key (`0.0.2`, `0.0.50`, `0.0.800`) and with the backend stopped. Each activation costs one `AccountInfoQuery` paid by the operator, 0.00119243 ℏ (measured). The CI is green. Not tested: the answer `null` on the network (only the message of the page and a unit test), a key of the account changed on the network after an activation, and browsers other than Edge. Observed later (lot Hygiene and security, note of 2026-10-15 in ADR 0019): `GET /accounts/0.0.11038285`, an account whose key is a list of two keys, answers `"key":null`; the other two points are still not tested.
20. **Done (lot Error handling, note of ADR 0014). The request bodies were not validated.** Observed: `POST /accounts/transfer` with the body `{}` returned HTTP 500 (a `TypeError` in `AccountId.fromString`). From the code: the DTOs have class-validator decorators, but no `ValidationPipe` was registered, and `CreateAccountDto` had no decorator. Result: a global `ValidationPipe` is registered in `AppModule`, `CreateAccountDto` has `@IsNumber()` and `@Min(0)`, and the same request answers HTTP 400 with the five invalid fields (observed with curl). The creation of an account and a transfer from the frontend still succeed (observed).
21. **A key that is not a private key gives a 500 on a transfer.** Observed (Swagger, 2026-10-13): `POST /accounts/transfer` with a public key typed in the field of the private key answered HTTP 500. The cause was not read in the backend log, so it is not known whether the error comes from the parsing of the key or from the signature. Envisaged: read the log first, then decide whether the DTO or the filter (ADR 0014) should turn it into a 400.
22. **The status of `POST /accounts` is not known.** From the code: the route is documented with the status 200. The real status was not observed. For `POST /accounts/transfer`, documented 200 as well, the real status was 201 (observed, corrected in ADR 0015). Envisaged: observe the status with Swagger and align the documentation.
23. **`page=abc` gives two validation messages, one of them misleading.** Observed with curl: `GET /tokens?page=abc` answers HTTP 400 with `page must not be less than 1` and `page must be an integer number`; the first one does not describe the value sent. The cause was not examined.
24. **Done (lot Configuration, ADR 0017). The HBAR transfer was paid by the sender, the token operations by the operator.** From the code: `transferHbar` created a client with the sender as operator at each call and never closed it, while the association and the transfer of tokens used the operator client, the sender only signing. The author chose that the operator pays every operation, for consistency with the tokens. Result: `transferHbar` sends the transfer with the shared client and the sender signs it. Observed (2026-10-13): a transfer of 1 ℏ from `0.0.10952224` to `0.0.6106565` answered `SUCCESS` with the transaction ID `0.0.6106565@1791924039.660729844` (the operator account first), and the balance of the sender went from `8.99891412` to `7.99891412` ℏ. The effect of the clients that were never closed was not observed. Not tested: a transfer from an account whose balance is too low, and the answer for a malformed account ID compared with the previous code. A risk that follows: the operator pays the fees for whoever reaches the API, which adds to item 7 (no authentication).
25. **Done (lot Strict TypeScript, ADR 0018, note of 2026-10-14 in ADR 0006). The CI did not build the backend.** Observed: `.github/workflows/ci.yml` had no step that runs `nest build`, while the frontend had its `build`. From the code: `ts-jest` compiles the files that the tests load, and which files of `backend/src/` they load was not examined, so a type error in a file that no test loads could have passed the CI. Result: the workflow runs `pnpm --filter backend build` after the end-to-end test. Observed by the author: the command ran without error on 2026-10-14, and the CI was green with this step on commit `1718c2a`. Not tested: that the step turns red on a type error (no failure was provoked on purpose).
26. **Done (lot Hygiene and security, ADR 0023). The backend reads a private key of 64 hexadecimal characters as Ed25519, whatever the type of the account.** From the code: `PrivateKey.fromString` is used in `transferHbar` (`accounts.service.ts`) and in the association and the transfer of tokens (`tokens.service.ts`). In a Node script run by the assistant with the SDK 2.68.0 (see ADR 0019), `PrivateKey.fromString` read such a key as Ed25519 even when it was an ECDSA key, which gives another public key and no error; so a transfer signed with the ECDSA key of an account, typed as 64 hexadecimal characters, would be signed with another key than the one of the account. Observed (2026-10-15, testnet): with the ECDSA account `0.0.6101287` and its key as 64 hexadecimal characters, a transfer of 1 ℏ and the association of a token both showed `INVALID_SIGNATURE`. The frontend reads the key with the type of the account (ADR 0019); the backend did not. Result: `readPrivateKey` (`backend/src/hedera/read-private-key.ts`) reads a key of 64 hexadecimal characters with the type of the account (one `AccountInfoQuery` paid by the operator) and a DER key as before, in `transferHbar`, `associateToken` and `transferToken`. Observed after the change: the same transfer and association, then a transfer of 5 tokens, answered `SUCCESS` with the ECDSA account; an Ed25519 account with its key as 64 hexadecimal characters, and the DER keys of both types, still worked; an unknown sender still answered HTTP 404 with the same body. A known limit, observed: for an account whose key is a list of keys (a threshold of 1 of 2 was created for the test), an ECDSA key as 64 hexadecimal characters is still read as Ed25519 and answers HTTP 400 `INVALID_SIGNATURE`, while its DER form works and the Ed25519 key works. Not tested: that limit with a token operation, a key with `0x` on the network, and a public key typed in the field (item 21).
27. **Done (lot Hygiene and security). Dead code and loose typing in the backend.** From the code: `app.module.ts` held 13 lines of commented-out code, `AccountsService` imported the SDK in several separate statements, `createAccount` returned `Promise<any>`, and `TopicsService` carried the `@ApiOperation` and `@ApiResponse` decorators of its routes, which the controller already has. Result: the code is removed, the imports merged, the return type of `createAccount` written out, and the decorators removed from the service. Observed by the author: the JSON of Swagger (`/api-json`) is identical before and after (11,890 bytes, same SHA256), so the decorators had no effect; the tests, the lint, the format check and the build pass, and the CI is green. Not tested: the Docker build.
28. **Done (lot Hygiene and security, note of 2026-10-15 in ADR 0014). A property that has no decorator was ignored by the validation.** From the code: the global `ValidationPipe` had no option, so a property that is not in the DTO, in a body or in a query, was accepted and dropped without a word. Result: the pipe uses `whitelist: true` and `forbidNonWhitelisted: true`, and such a request answers HTTP 400 with `property extra should not exist`. Observed by the author with curl on the running backend: `POST /accounts/transfer` with an extra property, and `GET /tokens?extra=1`; the list of tokens (`page` and `limit`), the creation of a topic, the publication and the reading of a message and an HBAR transfer still work from the frontend; an end-to-end test checks the message. Not tested after the change: the creation of an account and the token operations from the frontend.
29. **Done (lot Hygiene and security, note of 2026-10-15 in ADR 0006). The frontend had no format check.** Observed: the CI ran the Prettier check for the backend only, and `frontend/package.json` did not have Prettier. Measured by the assistant on a copy of `HEAD` with Prettier 3.9.10: the options of the backend (`singleQuote`) would have reformatted all the 26 files checked (about 260 lines, mostly quotes, because the frontend uses double quotes), and the default style 5 files (line breaks only). Result: `frontend/.prettierrc` holds `{ "endOfLine": "auto" }`, `prettier` `^3.9.10` is a dev dependency (resolved to 3.9.10, the version of the backend), `format` and `format:check` scripts check `{app,components,lib}/**/*.{ts,tsx,css}` and the `*.{ts,mjs}` files of the folder, the 5 files are reformatted, and the CI has the step `Frontend format check`. Observed by the author: `format:check`, the lint, the build and `pnpm install --frozen-lockfile` pass, and the CI is green. The lockfile also changed by a rewriting of four identifiers of the `eslint-*` packages (their peer dependencies are written out), without any change of version. Not tested: that the step turns red on a file that is not formatted, and the Markdown and JSON files, which the check does not cover.
